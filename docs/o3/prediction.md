# O3 扩错层：测量前预测

2026-11-13T14:00:00+08:00（正式测量前写入，不随后续结果回改）

## 问题

当工作负载落在写路径（`POST /api/enroll`，`-sync each`，每笔请求 `fsync` 落盘）时，增加 enrolld 实例数能否提升吞吐？即"扩实例"这一层是否是有效扩展。

## 已有依据（来自实验 2 与本机基线）

1. **单写者串行 fsync 上限约 780 次/秒。** 实验 2 任务 0 的 `bin/enrolld -bench-fsync 2000` 三次平均 fsync 耗时 1.274、1.300、1.265 ms，等权平均约 1.28 ms，推算单个写者串行 fsync 约 `1000/1.28 ≈ 781` 次/秒。来源：`ops-lab2-9/runs/task0-baseline/fsync-bench.txt`。
2. **fsync 负载下瓶颈在磁盘，不在 CPU。** 运行 `-bench-fsync 20000` 时，`vmstat` 采样 `wa` 为 46%～47%，而 `us+sy` 仅 3%～7%；`iostat` 的 `f/s` 约 1500～1570、`f_await` 0.03～0.04 ms。说明 CPU 不忙，主要成本在磁盘同步等待。
3. **所有实例共享同一块系统盘。** 本机数据目录 `data/` 位于 `/dev/vda1`（ext4），多个 enrolld 实例若使用同一数据目录或同一物理盘，其 `fsync` 会串行化在同一块设备的 flush 队列上。实验 2 `o3-write-light-01` 在 20 请求/秒、`sync=each` 下 `disk_util` 仅 0.038，说明低时尚未到瓶颈；但按 780 次/秒的串行上限，吞吐一旦接近该值，磁盘将成为共享瓶颈。

## 预测

- 1 实例在写路径下的吞吐上限受限于 `fsync` 串行速率，约为数百请求/秒量级（具体以实测为准，预计 400～700 请求/秒）；此时 `disk_util` 接近 1、`disk_w_await` 上升、CPU `iowait` 升高而 `us+sy` 不高。
- **增加到 2、4 实例不会线性提升写吞吐。** 因为所有实例共享同一块磁盘的 `fsync` 能力，多个实例的并发写入会在块设备层排队，串行化到约 780 次/秒的物理上限。预计总 `ok_rps` 与 1 实例相比增幅很小（可能不超过 20%），甚至因锁竞争和上下文切换反而下降；`disk_util` 仍接近 1。
- p99 延迟会随实例数增加而上升或维持高位：实例越多，每个实例分到的磁盘 flush 机会越少，单请求的 `fsync` 等待时间越长。
- 对照读路径（`/api/courses/1`，无 `fsync`）：增加实例应能提升吞吐（CPU 可并行），与写路径形成"扩对层"与"扩错层"的对照。

## 实验设计（预测阶段确定，测量时不回改）

- 写路径：`POST /api/enroll`，`-sync each`，负载 `200@120s`（超过单实例容量）。
- 对照组：1、2、4 个 enrolld 实例，均经 lbd 轮询，每实例相同 CPU 配额（25%）、内存、`work` 参数，共享同一 `data/` 目录（同一块盘）。
- 读路径对照组：1、2、4 实例，`GET /api/courses/1`，相同到达率，验证"扩对层"的线性度。
- 记录：`ok_rps`、`error_rate`、`p99_ms`、`disk_util`、`disk_w_await_ms`、`cpu_iowait`、`svc_cpu_busy`；每配置一轮，固定随机种子。
- 判定：若写路径下 `disk_util→1` 且 `ok_rps` 不随实例数增长，则"扩实例"是扩错层；若读路径下 `ok_rps` 随实例数增长，则对照成立。

## 局限

- 本结论限定于本机单块系统盘、`sync=each`、ext4、无独立数据盘的条件；若实例使用不同磁盘或 `sync=group/interval`，结论不同。
- 预测中的 780 次/秒来自 fsync 微基准，不等于 HTTP 写请求的真实吞吐（后者还有网络、解析、加锁开销），只作为"磁盘是共享瓶颈"的方向性依据。
